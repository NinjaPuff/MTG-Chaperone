Bug 1

Sideboard Basics Double-Counted

Basic lands in the sideboard are counted as being in both the main deck and the sideboard.

Root Cause

Two bugs compound in DeckBuilderPage.tsx:

Problem A: onBasicLandsChange strips sideboard basics

Line 1261 — filters out ALL basic land cards regardless of zone:

const nonBasicCards = deck.cards.filter(
  (card) => !BASIC_LAND_ORDER.includes(card.name)
);

When the BasicLandAdder popup is used, sideboard basics are removed and recreated as zone: 'main' on line 1279.

Problem B: deck.basicLands drifts out of sync

When cards are moved between zones via context menu (moveCardBetweenZones) or added from the pool (addCardToActiveDeck), deck.basicLands is never re-extracted. This causes the BasicLandAdder popup to show stale counts that don't match the actual card list.

Problem C: No way to intentionally add basics to the sideboard

The BasicLandAdderPopup only manages main-deck basics. There is no UI to add basic lands specifically to the sideboard — users have to find basics in the pool and right-click, which is awkward and error-prone. The modal needs a zone selector so users can manage sideboard basics directly.

Proposed Fix

Change Location Detail
Fix A DeckBuilderPage.tsx:1261 Change filter to preserve sideboard basics:
(card) => card.zone === 'sideboard' || !BASIC_LAND_ORDER.includes(card.name)
Fix B DeckBuilderPage.tsx Re-extract basicLands after addCardToActiveDeck and moveCardBetweenZones mutations by calling extractBasicCounts inline
Fix C BasicLandAdderPopup.tsx Add a Main / Sideboard tab switcher to the popup. Each tab manages its own counts independently. "Suggest Lands" only appears on the Main tab — never on Sideboard. Sideboard basics are stored as regular cards with zone: 'sideboard' in the cards array.

BasicLandAdder Popup — Updated Design

Main Deck
Sideboard
  • Two tabs: Main Deck (default) and Sideboard
  • Each tab shows +/- controls for each basic land type
  • "Suggest Lands" button only visible on the Main Deck tab
  • Sideboard tab changes create/update cards with zone: 'sideboard'
  • Main tab continues to use deck.basicLands + zone: 'main' as before

Bug 2

Deckbuilder Panel Not Sticking

The sidebar drifts away from the viewport edge. Recurring issue — keeps getting broken by other changes.

Root Cause

The sidebar stays pinned via a viewport-height CSS grid that prevents page scroll. There is no fallback if the page wrapper overflows (e.g., when the deck-tab header wraps or grows). When the combined height of header + work area exceeds the viewport, the page scrolls and the sidebar drifts out of view.

Current Layout Chain (fragile):

  • AppLayout main: flex min-h-0 flex-1 flex-col
  • AppLayout inner div: flex min-h-0 flex-1 flex-col w-full px-2 py-3
  • DeckBuilderPage wrapper: flex min-h-0 flex-1 flex-col space-y-2
  • Work area grid: lg:h-[calc(100dvh-9rem)] lg:overflow-hidden
  • Page wrapper has no overflow-hidden — if content grows, page scrolls

Proposed Fix

Prevent page-level scroll on desktop by adding overflow containment to the page wrapper. The internal scroll regions (pool list, deck list) still work via their own overflow-y-auto.

Change Location Detail
1 DeckBuilderPage.tsx:981 Add lg:overflow-hidden to the page wrapper div:
flex min-h-0 flex-1 flex-col space-y-2 lg:overflow-hidden
Why not sticky? The sidebar is inside a CSS Grid cell with a fixed viewport height. position: sticky only works relative to a scrolling ancestor — inside a height-locked grid cell it has no effect. The correct fix is preventing the scroll from happening in the first place.
Internal scrolling still works. lg:overflow-hidden only prevents the page from scrolling. All internal scroll regions are unaffected because they have their own overflow-y-auto:
  • deckbuilder-pool-scroll — pool card list scrolls vertically
  • deck-sidebar-main-scroll — main deck card list scrolls
  • deck-sidebar-sideboard-scroll — sideboard list scrolls (when expanded)
Test: Layout test asserting the page wrapper has overflow-hidden at lg breakpoint via class check on the data-testid element.
Bug 3

Landscape Cards Overflow on Mobile

Horizontal (split/battle) cards in the preview modal overflow the screen on mobile devices.

Root Cause

In cardLayout.ts (line 78), the touch-variant landscape frame uses viewport-relative width that ignores cumulative padding:

variant === 'touch'
  ? 'h-[min(55vh,400px)] w-[min(92vw,660px)]'

On a 375px phone:

  • 92vw = 345px (frame width)
  • Outer modal wrapper: p-4 = 32px
  • Inner dialog: p-4 = 32px
  • Available space: 375 - 32 - 32 = 311px
  • Frame (345px) > Available (311px) = overflow!

The frame also has shrink-0 which prevents it from fitting within the constrained container.

Proposed Fix

The dialog (cardHoverPreviewDialogClassName) already uses w-full max-w-2xl which naturally constrains width. The landscape frame should fill available dialog space instead of fighting it with viewport units.

Change Location Detail
1 cardLayout.ts:79-80 Touch variant size: change to 'h-[min(55vh,400px)] w-full'. The parent dialog already caps width via max-w-2xl.
2 cardLayout.ts:82 Make shrink-0 conditional on variant. Return different tail strings:
variant === 'touch' ? 'relative ... overflow-hidden ...' : 'relative ... shrink-0 overflow-hidden ...'

After fix — cardHoverPreviewLandscapeFrameClassName:

export function cardHoverPreviewLandscapeFrameClassName(
  variant: 'desktop' | 'touch' = 'desktop',
): string {
  const size =
    variant === 'touch'
      ? 'h-[min(55vh,400px)] w-full'
      : 'h-[min(60vh,440px)] w-[min(92vw,660px)]';
  const base = `relative ${size} max-w-full overflow-hidden rounded-md border border-border bg-muted/40`;
  return variant === 'desktop' ? `${base} shrink-0` : base;
}

Desktop keeps shrink-0 and explicit viewport width (flyout is not inside a constrained dialog). Touch drops both since it lives inside the width-constrained touch modal dialog.

Test: Unit test on cardHoverPreviewLandscapeFrameClassName('touch') asserting no viewport-width class and no shrink-0.
Bug 4

Mobile Report Dialog Auto-Focus

Opening the match report dialog on mobile immediately focuses the text input, triggering the virtual keyboard and pushing content up.

Root Cause

In ReportMatchDialog.tsx (lines 63-68), a useEffect unconditionally focuses the first input:

useEffect(() => {
  if (step !== 'entry') return;
  firstInputRef.current?.focus();
}, [step]);

No device check — fires on mobile and desktop alike.

Proposed Fix

The codebase already exports deviceHasHover() from CardPreviewContext.tsx which wraps window.matchMedia('(hover: hover)') with SSR safety. Import and use it:

import { deviceHasHover } from '@/components/cardpool/CardPreviewContext';
useEffect(() => {
  if (step !== 'entry') return;
  if (deviceHasHover()) {
    firstInputRef.current?.focus();
  }
}, [step]);

Uses the same detection pattern as the card preview system. SSR-safe (returns false when window is undefined).

Test: Mock window.matchMedia to return matches: false and assert .focus() is not called.
