MTG Chaperone · planning brief

Share a current-phase deck without making it public

Best path: share a frozen copy of the list contents behind a short unlisted URL — not access to the live deck record. Share button, copy modal, guest-readable page. Season decklistVisibility stays off.

Locked: active deck · snapshot of contents · no revoke in v1 · guest sees archive-style list (not the builder)

Recommended answer

Yes: the link should share the contents of the list as a viewable document, rendered in the same read-only chrome as the site, not grant ACL access to the owner's live Decklist row. Clicking Share freezes main/sideboard (names, quantities, images) into a snapshot. Later edits, unregisters, and deletes of the source deck do not change what the recipient sees. The token is only a lookup key for that frozen document.

How they get the link

Share on the active deckbuilder tab. Modal with URL and Copy. This is a snapshot of the list as it is now. No revoke in v1 — sending the list is the decision.

What the recipient sees

Guest page at /share/decks/:token. Same read-only archive surface: default to List (main/sideboard cards), with the existing List/Details toggle so curve/stacks are available. Not the deckbuilder. Not Details-only — in this app Details is the analytics view, not the card list people are sending.

What they do not get

No permission on the live deck. No pool. No other decks. No season archive. No revoke control in v1.

What the app does today

Deck access is all-or-nothing at the season flag. There is already a guest-capable spectator path, and already an invite-token analog. There is no unlisted middle state.

Course of action

  1. 1. Lock the product model: frozen list document, not live deck access

    Share copies the cards into a snapshot the site can render. Recipients never receive a permission on the source Decklist. The snapshot must not enroll anything into the season archive or change isDecklistVisibleToViewer.

  2. 2. Store the snapshot; keep the URL short

    Do not pack the whole list into the query string (length limits, ugly URLs). New row e.g. DecklistShare: unique token from crypto.randomBytes(18).toString('base64url'), frozen entries JSON, owner, optional origin decklistId for "shared from." No status/revoke field in v1. The origin FK is metadata only — view authorization is the token, not getDecklistById.

  3. 3. Put Share on the current-phase surface they already use

    Primary: deckbuilder header next to Import / Register, targeting the active deck tab. Modal copies https://…/share/decks/<token>. Secondary (nice): same action on the owner's own /decks archive row. Do not put Share on other players' rows.

  4. 4. Guest view is a new read-only route

    Reuse archive chrome: default List (DeckCardList main/sideboard), Details toggle for DeckAnalyticsView, editable={false}, fed by the snapshot payload, not GET /api/decklists/:id. Public GET by token. Unknown tokens return 404. No login wall. No Register/edit.

  5. 5. Plan first, then TDD

    Hand the prompt below to a planning agent. That agent should produce schema, APIs, a visibility matrix, UX, and a test list — not code. Implementation comes after the plan is accepted.

How a share actually moves

Owner creates a token. Recipient never needs an account. The season archive is not involved.

Why not the other options

Locked · recommended

Snapshot of list contents (short token URL)

  • Shares the cards, not access to the live deck
  • Guest sees the same read-only site chrome
  • Later edits do not leak
  • URL stays short
  • Season archive stays closed

Cost: store frozen entries on a share row. That is the right amount of work.

Not this

Live access grant on the deck row

Token would mean "you may call getDecklistById." Recipients would see later edits, unregister, and possibly empty lists. That is sharing access, which you asked to avoid.

Demote

Encode the whole list in the URL

Truly "the link is the data," but URLs get long and leak in logs. Store the snapshot; put only the token in the URL.

Reject

Turn decklistVisibility on

Makes every registered list browsable on /decks. That is "fully public," which is the thing you want to avoid.

Reject as the secret

Share /api/decklists/:uuid

Today this 403s when visibility is off. If you special-case "has the id," every UUID that ever leaked in an owner response becomes a permanent backdoor. Tokens exist so the secret is separate and rotatable.

Demote

Password, named recipients, or login wall

Passwords add friction to "send a link." Named recipients require accounts. A login wall contradicts "account or not." Fine as later options, not v1.

Share button and modal — yes

That is the right get-the-link UX. Mocked in this app's own chrome (small header buttons, ConfirmDialog-style overlay). Keep the new control shrink-0 so the deckbuilder height chain does not break.

Risks the plan must not skip

  • Forwarded Discord links are public to that channel. There is no unsend in v1. Copy should say sharing is a choice.
  • Snapshot payload must include enough to render without a second authorized deck fetch (card names, quantities, zones, image URIs).
  • Referrer leakage if the guest page links out. Prefer referrerpolicy / noindex.
  • Share in the deckbuilder header can break the height chain. Layout rule is non-negotiable.
